# Paw:Paw 통합 기획 스펙 (v2 · 최종)

> 이전 대화에서 나온 모든 결정사항을 통합한 최종본입니다. `docs/features/*.md`는 이 문서를
> 기능별로 더 상세히 풀어놓은 것이므로, 작업 시 두 문서를 함께 참고하세요.

## 1. 프로젝트 성격
- 반려동물 건강관리 웹 서비스, **포트폴리오/시연용** (실사용 서비스 아님)
- AI 챗봇은 학교 제공 HAI-GPT API를 사용하며, 월간 토큰 할당량 제한(개발기 5,000 / 개강 후 20,000)이 설계 전반에 영향을 줌

## 2. 확정된 기술 스택
| 분류 | 기술 |
|---|---|
| Frontend | React (Vite) + Tailwind CSS v4 |
| Backend | FastAPI (Python) |
| DB | MongoDB Atlas |
| 인증 | Kakao 소셜 로그인 + JWT 세션 |
| AI | HAI-GPT (ChatGPT 계열, 학교 발급 키) |
| 알림 | 인앱 알림 (복약·예방접종만, 벨 아이콘) — 카카오 알림톡은 발신 대행사 계약 필요해 범위 밖 |
| 배포 | Vercel / Railway |

## 3. 스코프 확정 (제외된 것들)
- ❌ 커뮤니티 기능 (자랑 피드/게시판) — 완전 제외
- ❌ 회원가입 모달 — 반려인 정보는 카카오 로그인으로만 수집
- ❌ 반려동물 추가/설정 실시간 미리보기 패널 — 제외
- ❌ 개발자 로그 버튼 — 프로덕션 화면에서 제거 (보안 이슈)

## 4. 온보딩 흐름
0. 비로그인 상태로 `/` 접속 → **인트로 페이지** 노출 (서비스 소개 + 카카오 로그인, `docs/features/intro.md`)
1. Kakao 로그인 (반려인 정보는 카카오에서 받아옴, 별도 회원가입 폼 없음)
2. 로그인 성공 → **메인페이지**로 리다이렉트. 반려동물이 없으면 빈 상태(등록 유도 버튼)만 노출
3. 반려동물 **기본정보**(이름·나이·종)는 사용자가 직접 입력
4. 반려동물 **세부정보**(복약·예방접종)는 AI 챗봇과의 대화를 통해 등록 — 6장 참고

## 5. 화면 구성
- **인트로 페이지** (신규 추가): 로그인 전 첫 진입 화면
- NAV(로그인 후 공통): 대시보드 / AI챗봇 / 건강 레포트 / 마이펫이지
- **메인페이지**(로그인 후 첫 화면, 간소화 대시보드): 중앙 마스코트 애니메이션 자리 + 알림 우선순위 기반 말풍선 + 좌측 축소 위젯. 상세는 `docs/features/dashboard.md` 참고
- 전체 대시보드, AI 챗봇, 건강 레포트, 마이펫이지, 반려동물 추가/설정
- **품종 가이드**: 별도 화면이 아니라 건강 레포트 상단에 고정 노출되는 하위 요소. 상세는 `docs/features/breed-guide.md` 참고
- 세부 화면별 스펙은 `docs/features/*.md` 참고 (신규: `intro.md`, `breed-guide.md`)

## 6. AI 챗봇 아키텍처 (핵심 설계)

### 6.1 두 개의 병렬 감지기
챗봇은 "모드 전환"이 아니라, 사용자의 모든 메시지가 **두 감지기를 동시에 통과**하는 구조로 동작한다.

| 감지기 | 항상 동작 | LLM 호출 필요 여부 | 결과 |
|---|---|---|---|
| 증상 감지기 | O | O (자유 상담 답변 생성 시 같이 처리) | '뽀삐의 건강'에 병명 없이 조용히 기록 |
| 등록 감지기 (복약/예방접종) | O | ✕ (키워드/정규식 매칭, 토큰 소모 없음) | "등록할까요?" 제안 → 슬롯필링 시작 |

> 참고: 사용자가 모드를 명시적으로 선택하게 할지 재검토했으나, 위 병렬 감지기 구조(모드 전환 없음)를 그대로 유지하기로 확정했다. 증상 감지 자체도 명백히 무증상인 메시지는 규칙 기반으로 걸러내되, 애매한 경우는 별도 API를 추가 호출하지 않고 위 표의 통합 호출 결과(`isSymptomDetected`)를 그대로 판별 기준으로 쓴다 — 7장 원칙 3 "호출을 나누지 않는다"와 일치.

> 참고: 백엔드 실제 명세(`docs/API_SPEC.md` §2.3)는 `/chat/query`+`/chat/summary` 자유대화 흐름만 다루고 등록 흐름을 명시하지 않는다. 이 문서의 등록 감지기(슬롯필링, `docs/features/chatbot-registration.md`)는 `docs/API_SPEC.md`와 무관하게 별도 병행 경로로 유지한다 — 절대 규칙 4번(키워드/버튼 처리 가능 로직은 LLM 호출 안 함)과 카카오 알림 오발송 리스크 때문.

### 6.2 등록 슬롯필링 흐름
자유 텍스트 파싱 대신 **버튼/피커 기반 단계별 질문**으로 데이터를 채운다 (오답 가능성 최소화, LLM 호출 없음).

1. 반려동물 선택 (버튼)
2. 항목별 질문 — 아래 두 패턴 중 하나
3. 요약 카드 확인 (확인/수정)
4. 저장 → 리스트 모달에서 언제든 재수정 가능

### 6.3 등록 데이터 스키마 (두 패턴으로 일반화)
알림 대상은 복약·예방접종 두 가지뿐이며, 실제로는 아래 2개 패턴으로 수렴한다.

| 패턴 | 대상 | 필요 입력 | 리마인드 |
|---|---|---|---|
| 반복형 | 복약 | 반려동물, 약이름, 하루 횟수(1~5), 알림시간(최대 3회) | 매일 지정 시간 |
| 단일날짜형 | 예방접종 | 반려동물, 항목명, 날짜 | 1주전·1일전·당일 (고정값, 사용자가 정하지 않음) |

```json
{
  "petId": "string",
  "type": "medication | single_date",
  "title": "string",
  "frequencyPerDay": "number (medication만)",
  "alertTimes": ["HH:mm", "... (medication만, 최대 3개)"],
  "date": "YYYY-MM-DD (single_date만)"
}
```

### 6.4 병명 표기 규칙 (매우 중요)
- 챗봇이 사용자에게 주는 **답변 자체**: 병명 언급 가능 ("관절염일지도 모릅니다", 통계·출처 포함)
- **대시보드에 자동 업로드되는 기록**: 병명 절대 금지 ("다리 절뚝임(시작: 3일전)" 수준까지만)
- API 필드로는 `symptomSummary`(병명 금지, 대시보드 저장용) / `suspectedSymptom`(병명 가능, 요약 모달 전용)로 분리
- **출처 표기는 아래 고정 카테고리 라벨 3종만 사용한다** (구체적인 문서/논문명을 지어내지 않는다 — fabrication 방지):
  - "일반 수의학 상식"
  - "품종별 유전질환 정보"
  - "등록된 데이터 기반 추정"
  - `answerText`/`suspectedSymptom`/건강 레포트의 `diagnosisOpinions[].text`에 붙는 모든 `[출처: ...]`에 동일하게 적용.

### 6.5 품종 가이드 컨텍스트 주입
- 캐싱된 품종 가이드(`docs/features/breed-guide.md`)는 챗봇 답변 생성 시 시스템 프롬프트에 **사용자에게 노출되지 않고 조용히** 포함되어 답변 품질만 높이는 용도로 쓰인다.
- 챗봇 화면에는 품종 가이드를 UI로 노출하지 않는다 (UI 노출은 건강 레포트 상단 고정 영역뿐).

### 6.6 HTTP 응답 스키마 매핑
- 챗봇 상담모드의 LLM 출력 JSON(`answerText`/`isSymptomDetected`/`symptomSummary`/`suspectedSymptom`, `scripts/prompt-test/prompts.py`에서 검증 완료)과 `/chat/query`의 실제 HTTP 응답 스키마는 별개 레이어다.
- LLM 출력 스키마는 이미 검증되었으므로 변경하지 않는다. HTTP 응답으로 나갈 때는 라우트 핸들러에서 순수 후처리(파이썬 매핑)로 `reply`/`detectedSymptom{area,description}`/`suspectedSymptom` 형태로 변환한다 — 추가 LLM 호출 없음. 상세 매핑은 `docs/features/chatbot-consult.md` 참고.

## 7. 토큰 절약 설계 원칙
1. **등록 감지기는 LLM을 쓰지 않는다** — 키워드/정규식 매칭으로 처리
2. **슬롯필링 UI는 텍스트 생성이 필요 없다** — 버튼/피커로만 구성
3. LLM 호출은 **자유 상담 답변 생성**에만 사용 (답변 + symptomSummary + suspectedSymptom을 한 번의 호출로 같이 받기 — 호출 횟수 최소화)
4. 프롬프트에 대시보드 데이터 전체를 넣지 않고, 최근 체중/최근 특이사항 등 요약본만 전달
5. `max_tokens` 캡을 걸어 응답 길이 제한
6. 개발 기간(월 5,000토큰)에는 목업 응답 모드로 개발하고, 실제 API 호출은 프롬프트 검증 시에만 최소한으로 사용
7. 발표/시연 날에는 실시간 호출 대신 사전에 캐시해둔 응답을 재생하는 방식을 권장
8. 할당량 소진 시 "AI 상담이 일시적으로 제한됩니다" 같은 안내로 우아하게 처리 (에러로 죽지 않게)
9. 반복 질문은 정규화된 질문 텍스트를 기준으로 캐싱한다 (TTL 설정 — 동일 질문 재호출 방지)
10. 품종 가이드는 품종당 1회만 생성해 DB에 캐싱하고, 동일 품종 재등록 시 재사용한다 (재호출 안 함)
11. 건강 레포트는 기간 내 참고 데이터(체중/복약/예방접종/증상)에 변화가 없으면 재생성을 스킵하고 캐싱된 레포트를 재사용한다

## 8. 알림 연동 (인앱 알림 — 카카오톡 알림톡 대체)
> **변경 사유**: 카카오 알림톡은 카카오 로그인과 완전히 별개 시스템으로, 실제 발송에는 카카오 비즈니스 채널 + 사전 승인된 템플릿 + 솔라피/알리고/NHN Cloud 같은 유료 발신 대행사 계약이 필요하다. 이 프로젝트엔 그런 계정/키가 없고(포트폴리오/시연용, 실사용 트래픽 목표 아님), 무료로 계속 보낼 방법도 없어 도입하지 않기로 했다. 대신 외부 의존성 없이 실제로 동작하는 **인앱 알림(Navbar 벨 아이콘)**으로 대체한다 — "복약·예방접종 두 가지만 알림 대상으로 한다"는 원래 규칙의 취지는 그대로 유지, 발송 채널만 바꾼다.
- 복약 알림: 지정 알림시간이 지났고 아직 오늘 복용 체크가 안 된 경우 벨 아이콘에 표시. `GET /api/v1/pets/{petId}/notifications`로 조회, `PATCH .../notifications/{notificationId}/read`로 읽음 처리
- 예방접종 D-Day: 1주전/1일전/당일에 동일한 방식으로 벨 아이콘에 표시
- 별도 스케줄러 없이, 조회 시점에 "지금 떠야 하는 알림"을 온디맨드로 계산한다 (읽음 여부만 `notificationReads` 컬렉션에 저장)
- `docs/API_SPEC.md` §3.4의 `POST /api/v1/callback/kakao-medication`(카카오톡 웹훅)은 이 대체 설계로 인해 사용하지 않는다

## 9. 외부 스펙 문서 연동
- 실제 백엔드 wire-format의 권위 있는 참고 문서는 `docs/API_SPEC.md`(백엔드 개발자 김학래 작성)다. 이 SPEC.md와 겹치는 부분은 `docs/API_SPEC.md`를 실제 구현 기준으로 우선한다.
- 두 문서가 다른 지점을 발견하면 `docs/features/*.md` 각 파일에 정합화 내역을 남기고, 백엔드와 확인이 필요한 항목은 별도로 질문지를 만들어 전달한다.
- **범위 밖으로 남겨둔 항목**: 대시보드 API 구조 불일치 — `docs/API_SPEC.md`는 전역 `GET /api/v1/dashboard`(활성 펫 기준)를 가정하지만, 이미 구현된 백엔드는 펫별 `GET /api/v1/pets/{petId}/dashboard`를 쓴다. 이번 챗봇/건강레포트/품종가이드 정합화 라운드에서는 다루지 않았으니, 다음 협의 때 반드시 짚고 넘어갈 것.
- **카카오 알림톡 → 인앱 알림 대체**: 위 8장 참고. `docs/API_SPEC.md` §3.4(카카오 웹훅)와 어긋나는 지점이며, 김학래 확인 필요.
